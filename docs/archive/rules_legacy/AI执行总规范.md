# AI 执行总规范

**目的**：把分散的工作流、PRD、产物、提交和记忆规则收束成一条 AI 可直接执行的主线，减少跳文档、漏步骤和中途忘记规则。

**适用对象**：在 `E:\Codex\New_rules` 中执行的所有文档审查、PRD 相关工作、产物留档、原型绑定、`.docx` 交付、Git 留痕和会话记忆任务。

---

## 1. 只有一条主线

AI 执行时只按下面顺序思考：

1. 先判断任务类型
2. 再选唯一主路径
3. 再读取必要的专项附件
4. 再执行
5. 再验证
6. 最后才宣称完成

不要同时套多个路径，不要把前期稿和正式稿混成一个版本，不要把草稿当正式交付。

---

## 2. 必须先读什么

开始任何工作前，固定读取顺序如下：

1. [`AGENTS.md`](/E:/Codex/New_rules/AGENTS.md)
2. [`docs/AI执行总规范.md`](/E:/Codex/New_rules/docs/AI执行总规范.md)
3. [`docs/AI执行短版清单.md`](/E:/Codex/New_rules/docs/AI执行短版清单.md)
4. 当前任务对应的专项附件

专项附件只解决“怎么做”的细节，不替代总规范。

---

## 3. 任务分类

先把任务分到唯一一类，再执行：

- 文档评审
- PRD 产出或 PRD 改写
- 原型绑定或原型归档
- `.docx` 交付
- Git 提交或版本留档
- 会话记忆沉淀
- 其他普通任务

如果任务同时包含多个类目，先处理主类目，再处理附属类目。不要在没有主类目的情况下并行乱跑。

---

## 4. 通用执行顺序

所有任务都遵守这个顺序：

1. 识别任务类型
2. 确认当前阶段
3. 读取对应规则
4. 执行任务
5. 做门禁检查
6. 做版本或留档动作
7. 输出结果

### 4.1 阶段判断

- 探索阶段：只做收敛、澄清、草案
- 正式阶段：必须使用正式模板和正式留档规则
- 冻结阶段：只能按冻结版本推进，修改要走变更
- 归档阶段：只做留痕、绑定、快照和归档，不再随意改正文

### 4.2 统一原则

- 先验证，再判断
- 先门禁，再流转
- 先冻结，再交付
- 先留痕，再覆盖
- 先绑定，再归档

---

## 5. 文档评审路径

文档评审只看问题，不先看修辞。

### 5.1 标准组合

默认使用：

1. `superpowers:receiving-code-review`
2. `superpowers:dispatching-parallel-agents`
3. `documents`
4. 若对象明显属于 PRD 或 PRD 流程文档，额外启用 `prd-max`

### 5.2 评审目标

重点找：

- 遗漏
- 矛盾
- 歧义
- 不可执行点
- 不可测试点
- 风险点
- 版本或口径冲突

### 5.3 评审输出

评审结论必须落到文档或可执行修改建议里，不能只停留在口头判断。

---

## 6. PRD 路径

PRD 任务必须分阶段处理，不得混用模板。

### 6.1 选模板

- 前期需求探讨、问题定义、范围收敛、方案草案：使用 [`docs/PRD工作流复用模板.md`](/E:/Codex/New_rules/docs/PRD工作流复用模板.md)
- 正式评审、需求冻结、研发交付、测试验收、最终归档：使用 [`docs/standard-prd-template.md`](/E:/Codex/New_rules/docs/standard-prd-template.md)

### 6.2 PRD 硬规则

- 前期稿和正式稿不得混用同一文件反复覆盖
- 进入正式评审后，必须切换到正式模板
- 正式 PRD 必须可追踪、可验证、可冻结、可交付
- 任何功能点都要能回到页面、状态、交互、规则和异常

### 6.3 PRD 评审前门禁

进入正式评审、冻结或交付前，先确认：

- PRD-原型一致性矩阵
- PRD-原型一致性门禁
- 高保真原型可交互门禁
- 原型交互验收
- 需求交付包输出
- 原型绑定记录

少一项，都不能按正式交付推进。

---

## 7. 原型与交付包

### 7.1 原型

- 正式原型必须可点击、可验证、可回溯
- 不能只交截图、静态导出或录屏
- 正式原型的绑定记录固定为 `docs/prototype/<文档名>/binding.md`
- 正式原型的归档目录固定为 `docs/prototype/<文档名>/archive/<文档名>_v<版本号>_<YYYYMMDD>/`

### 7.2 交付包

- 交付包必须和冻结版本一致
- 交付包必须列出完整输出物
- 交付包缺项，不能算完成
- 交付包必须能追溯到需求编号、冻结版本和确认记录

---

## 8. `.docx` 路径

`.docx` 只是正式 Markdown 内容的派生物，不是源头。

### 8.1 规则

- 先完成 Markdown 正文
- 再完成评审和冻结
- 再生成 `.docx`
- 再更新绑定记录
- 再和 Git 历史一起留存

### 8.2 关键限制

- `.docx` 必须和对应 Markdown 一一对应
- 不允许一个 `.docx` 对应多个 Markdown
- 不允许一个 Markdown 对应多个正式 `.docx`
- `.docx` 的正式路径和绑定规则遵循 [`docs/docx产物链路说明.md`](/E:/Codex/New_rules/docs/docx产物链路说明.md)

## 10. 会话记忆

涉及跨会话协作、长任务延续、上下文压缩风险或决策沉淀时，遵循 [`docs/会话记忆强制执行规则.md`](/E:/Codex/New_rules/docs/会话记忆强制执行规则.md)。

原则是：

- 不能只在会话结束时总结
- 关键结论、待办、风险和未决问题要持续写入
- 需要沉淀时优先使用 `notion-knowledge-capture`

---

## 11. 执行时的自检清单

每次准备结束前，至少检查下面 6 项：

- 我是否判断了任务类型
- 我是否只走了一条主路径
- 我是否读了对应规则
- 我是否完成了门禁
- 我是否做了版本或留档动作
- 我是否把结果落到可追踪产物里

如果有任一项答不上来，就不要宣布完成。

### 11.1 短版执行口令

如果只保留一句最短的执行提醒，就是：

**先判类目，先看短清单，再读总规范，再进专项附件。**

---

## 12. 最短执行口令

如果要把这套规则压成一句话，执行顺序就是：

**先判类目，后读规则，先过门禁，再做产物，最后留痕。**

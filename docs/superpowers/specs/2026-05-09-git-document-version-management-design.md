# Git 文档版本管理设计说明

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this design task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为 `E:\Codex\New_rules` 建立一套“Git 仓库级版本管理 + 文档级发布快照”并行的文档治理方案，确保正文、历史版本、审阅记录和回滚路径可追溯、可对比、可恢复。

**Architecture:** 采用双层版本体系。Git 负责仓库级审计、审阅和回滚，`docs/versions/` 负责文档级正式快照与对外发布留档。主文档始终保持当前生效版本，正式发布时生成快照、递增文档版本号、提交 Git 标签或发布记录，形成“正文 + 快照 + 提交记录”的闭环。

**Tech Stack:** Git、PowerShell、Markdown、现有 `docs/versions/` 目录、现有文档规范体系。

---

## 1. 背景与目标

当前仓库已经有较完整的文档规范，包括：

- [产品需求管理流程规范](/E:/Codex/New_rules/docs/产品需求管理流程规范.md)
- [工作产出物管理规则](/E:/Codex/New_rules/docs/工作产出物管理规则.md)
- [文档仓库提交规范](/E:/Codex/New_rules/docs/文档仓库提交规范.md)

这些规范已经解决了文档内容本身的版本、归档和快照问题，但还没有把 Git 作为仓库级别的统一审计层纳入正式工作流。

本设计要解决的核心问题是：

- 正文修改靠什么控制
- 历史快照和 Git 提交如何对应
- 正式发布时如何形成稳定版本
- 回滚时应该回到哪一层
- 如何避免“文档版本号”和“Git 提交”各说各话

### 1.1 设计范围

本设计只定义 Git 视角下的仓库级版本管理方式，包括：

- 分支策略
- 提交策略
- 标签策略
- 快照与提交的对应关系
- 回滚和审阅的门禁

### 1.2 不在本设计范围内的内容

以下内容不由本设计展开，只引用现有独立规范：

- 需求流程节点、审批和责任划分
- 工作产出物的定义、归档和生命周期
- PRD 文档模板和章节结构
- 节点执行技能路由

这些内容分别由现有主流程规范、工作产出物管理规则、PRD 模板和流程执行技能附录承载。

## 2. 设计原则

1. **双层版本源**
   - Git 负责仓库历史、审阅轨迹、提交审计。
   - `docs/versions/` 负责正式文档快照和对外发布留档。

2. **正文单一真源**
   - 主文档路径中的当前文件始终表示“当前生效正文”。
   - 不允许同时维护多个彼此不一致的“当前正文”。

3. **正式发布必留快照**
   - 每次正式修订前必须先生成文档级快照。
   - 快照文件与 Git 提交必须能互相对应。

4. **Git 只管仓库级，文档版本只管内容级**
   - Git 不替代文档版本号。
   - 文档版本号不替代 Git 提交记录。

5. **最小扰动**
   - 既有目录结构尽量不改。
   - 只增加少量固定规则，不引入复杂分支流派。

6. **先快照后提交**
   - 任何会影响正式内容的修改，先留文档快照，再提交 Git。

## 3. 方案对比

### 3.1 方案 A：只用 Git

做法：
- 不再使用 `docs/versions/`
- 所有历史直接靠 Git commit / tag / branch 管理

优点：
- 简单，单一版本源
- 回滚方便

缺点：
- 不适合文档型仓库的正式发布留档
- 对非技术读者不直观
- 难以形成“可交付快照文件”

结论：
- 不推荐。它会和你现有的文档治理体系冲突。

### 3.2 方案 B：只用文档快照

做法：
- 继续只靠 `docs/versions/`
- Git 只当普通代码托管工具

优点：
- 贴合你现有习惯
- 文档对人更友好

缺点：
- 仓库级审计弱
- 变更轨迹、审阅轨迹、责任链不够统一
- 难以形成明确的协作门禁

结论：
- 不推荐。无法充分利用 Git 的审计能力。

### 3.3 方案 C：双层版本体系

做法：
- 主文档保持当前生效正文
- 正式发布时生成 `docs/versions/` 快照
- Git 记录提交历史、分支、标签和审阅轨迹

优点：
- 同时满足人类可读快照和机器可审计历史
- 与现有文档规范兼容
- 回滚、审阅、归档都更清晰

缺点：
- 需要固定少量流程规则
- 维护时要严格遵守先快照后提交

结论：
- 推荐采用。本设计的最终方案。

## 4. 总体架构

### 4.1 三层对象

1. **主文档层**
   - 当前正在生效的文档正文
   - 例如：`docs/产品需求管理流程规范.md`

2. **快照层**
   - 正式修订时生成的历史版本文件
   - 例如：`docs/versions/产品需求管理流程规范_v1.7_20260509.md`

3. **Git 层**
   - 记录工作区的变更历史、审阅轨迹、回滚点和发布标记
   - 通过 commit、branch、tag、release note 管理

### 4.2 三层职责

| 层级 | 职责 | 不负责什么 |
|---|---|---|
| 主文档层 | 维护当前生效正文 | 不负责保存全部历史 |
| 快照层 | 保存正式发布时的固定版本 | 不负责描述仓库协作历史 |
| Git 层 | 保存修改轨迹、协作轨迹和回滚点 | 不替代正式文档版本号 |

## 5. 分支与提交规则

### 5.1 分支策略

- `main` 只保留稳定、可发布版本。
- 正式修改必须先创建工作分支。
- 每个工作分支只处理一个主题或一个修订轮次。

建议分支命名：

```text
docs/<主题>
fix/<问题>
review/<轮次>
```

示例：

```powershell
git switch -c docs/prd-workflow-update
```

### 5.2 提交原则

- 每次提交只表达一类变更。
- 正文修改、快照生成、规范更新尽量不要混成一个不可解释的大提交。
- 提交信息必须能看懂“改了什么”和“为什么改”。

推荐提交类别：

- `docs:` 文档正文或规范修改
- `chore:` 规范、目录、命名、辅助文件调整
- `fix:` 对错误规则、错误链接、错误编号的修正

### 5.3 提交节奏

建议节奏如下：

1. 创建工作分支
2. 修改正文
3. 生成文档快照
4. 校验主文档和快照一致
5. 提交 Git
6. 如属于正式发布，再打标签

## 6. 文档快照规则

### 6.1 什么时候生成快照

以下情况必须生成 `docs/versions/` 快照：

- 正式修订前
- 正式发布前
- 版本号递增时
- 需要留存稳定基线时

### 6.2 快照文件命名

推荐命名：

```text
docs/versions/文档名_v版本号_YYYYMMDD.md
```

示例：

```text
docs/versions/产品需求管理流程规范_v1.7_20260509.md
```

### 6.3 快照与正文关系

- 快照必须与生成时的主文档内容一致。
- 主文档修改后，如内容已经发生正式变化，应重新生成对应快照。
- 快照是正式留档，不是临时备份。

### 6.4 快照与 Git 的对应关系

- 每次快照生成后，应在 Git 中形成对应提交。
- 如有正式发布，还应增加标签或发布说明。
- 快照文件名、文档版本号、提交说明三者应能互相检索。

---

## 7. 标签与发布规则

### 7.1 Git 标签用途

Git 标签用于标记“仓库级正式发布点”，不是替代文档版本号。

建议标签命名：

```text
docs/<文档名>/v<版本号>
```

示例：

```text
docs/product-requirements-process/v1.7
```

### 7.2 发布时点

建议在以下情形打标签：

- 文档进入正式发布状态
- 形成可对外分发的稳定基线
- 需要后续回滚的关键节点

### 7.3 标签与快照关系

- 标签指向 Git 提交。
- 快照指向文档文件。
- 两者共同构成正式发布基线。

---

## 8. 回滚规则

### 8.1 回滚优先级

回滚时优先级如下：

1. 最近一次稳定 Git 标签
2. 最近一次正式快照
3. 最近一次可解释的提交

### 8.2 回滚原则

- 单文件误改：优先恢复主文档，再补齐快照。
- 版本内容错误：先恢复快照，再重新发布。
- 仓库级错误：以标签为基准回退。
- 不要直接对历史文件做覆盖式修补，必须保留痕迹。

### 8.3 回滚记录

每次回滚都应记录：

- 回滚原因
- 回滚对象
- 回滚来源
- 执行人
- 影响范围

---

## 9. 审阅与合并规则

### 9.1 审阅对象

审阅重点不是“文字好不好看”，而是：

- 是否改变流程口径
- 是否影响责任边界
- 是否影响版本规则
- 是否影响快照一致性

### 9.2 合并门禁

合并到 `main` 前必须确认：

- 主文档与快照一致
- 版本号已递增
- 变更理由已记录
- 没有未解释的临时文件

### 9.3 禁止事项

- 禁止只改主文档不留快照
- 禁止只留快照不提交 Git
- 禁止正文和快照版本号不一致
- 禁止把草稿当正式版合并

## 11. 落地执行约束

### 11.1 最小落地组合

最小可执行组合为：

- 主文档版本号
- `docs/versions/` 快照
- Git 提交记录
- Git 标签

### 11.2 不可绕过规则

以下动作不得绕过：

- 正式修订前先生成快照
- 快照生成后再提交 Git
- 正式发布时再打标签
- 回滚时先回到稳定基线再改正文

### 11.3 适用边界

此方案适用于：

- 制度文档
- 流程规范
- PRD 与需求管理文档
- 工作产出物管理类文档

不建议直接套用于：

- 临时讨论稿
- 纯个人草稿
- 一次性参考材料

---

## 12. 结论

推荐采用“双层版本体系”：

- Git 作为仓库级历史源
- `docs/versions/` 作为文档级正式快照
- 主文档作为当前生效正文

这套模式最适合你现在这类以制度、流程、PRD 和版本快照为主的仓库，能同时满足：

- 回滚
- 审阅
- 追溯
- 发布留档
- 人类可读

同时，它也不会推翻你已经建立起来的文档治理体系。

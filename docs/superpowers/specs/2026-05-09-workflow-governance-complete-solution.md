# 工作流治理完整解决方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this solution task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将 `E:\Codex\New_rules` 的文档治理链路收敛为单一入口、统一快照口径、独立 `.docx` 产物链路和可迁移的版本管理体系，消除总入口争夺规则权威、快照路径混用和 `.docx` 游离的问题。

**Architecture:** 采用“四层治理”架构：总入口只负责导航，权威规范负责定义正文规则，快照与 `.docx` 分别承载 Markdown 正式留档与正式交付留档，Git 负责仓库级审计与回滚。所有链路都以 Markdown 冻结稿为中心，任何派生产物都必须与它建立可追溯绑定关系。

**Tech Stack:** Markdown、Git、PowerShell、现有 `docs/` 规范体系、`docs/versions/` 快照目录、`docs/docx/` 交付目录、`render_current/` 临时渲染目录。

---

## 1. 问题定义

当前工作流已经有主干，但还存在三类结构性问题：

1. 总入口可能被误用为新的规则源。
2. 版本快照目录的权威口径需要统一到分层目录。
3. `.docx` 文件已经存在，但它的生成、归档和版本对应关系还没有被完整纳管。

这三个问题的本质不是内容不够，而是**治理边界不清**。  
如果不先把边界定死，后续新增规范、计划、脚本和导出动作都会继续放大混乱。

---

## 2. 最终原则

### 2.1 总入口只导航，不仲裁

`docs/工作流总入口.md` 只做索引，不定义规则，不参与优先级仲裁，不替代任何权威规范。

### 2.2 Markdown 是正文源

所有正式内容以 Markdown 冻结稿为准。`.docx` 只允许作为派生产物，不允许反向作为正文编辑源。

### 2.3 快照是正式留档

正式快照只保存冻结后的 Markdown 版本，不承担 `.docx` 的职责。

### 2.4 `.docx` 是正式交付件或正式归档件

`.docx` 必须有明确归属目录、明确版本号、明确来源 Markdown 快照和明确用途。

### 2.5 旧平铺快照只读兼容

旧平铺快照可保留历史引用，但不得再作为新生成目标。

- 若 Git 提交规范与主流程规范冲突，以主流程规范为准。
- 若 PRD 模板与自由写法冲突，以 PRD 模板为准。

## 4. 总入口规则

### 4.1 定位

`docs/工作流总入口.md` 只做导航，不做规则定义。

### 4.2 必须包含的内容

总入口只允许写以下四类信息：

- 先读什么
- 每份文档管什么
- 哪些是主干、哪些是附录
- `.docx` 产物链路在哪

### 4.3 明确禁止的内容

总入口不得写：

- 新的优先级体系
- 新的版本管理规则
- 新的提交规则
- 新的责任模型
- 新的模板规则

### 4.4 必须写死的一句话

`docs/工作流总入口.md` 必须明确写入：

- 仅作索引，不构成任何规则优先级
- 与 `AGENTS.md`、`会话记忆强制执行规则.md`、`文档仓库提交规范.md` 冲突时，一律以后者为准

这样总入口只会是导航，不会演化成第二个 `AGENTS.md`。

## 5. 快照权威口径

### 5.1 正式口径

正式快照统一使用以下结构：

```text
docs/versions/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.md
```

示例：

```text
docs/versions/产品需求管理流程规范/产品需求管理流程规范_v1.8_20260509.md
docs/versions/工作产出物管理规则/工作产出物管理规则_v1.1_20260509.md
docs/versions/文档仓库提交规范/文档仓库提交规范_v1.1_20260509.md
```

### 5.2 目录职责

- `docs/versions/<文档名>/`：该文档的正式历史快照目录
- `docs/versions/<文档名>/<文档名>_v...md`：该文档的正式快照文件

### 5.3 旧平铺快照边界

旧平铺快照的处理规则如下：

- 可以保留
- 只读兼容
- 仅用于历史引用或回滚参考
- 不再作为新生成目标
- 不再作为脚本默认输出目标

### 5.4 迁移硬边界

从本方案生效后：

- 新快照不得再生成到平铺目录
- 新文档版本不得再以平铺路径作为正式示例
- 所有新的脚本、模板和命令示例必须默认使用分层目录

### 5.5 回滚优先级

回滚时优先按以下层级寻找：

1. 最近一次稳定 Git 标签
2. 最近一次 Markdown 正式快照
3. 最近一次可解释的提交

## 6. `.docx` 产物链路

### 6.1 `.docx` 的身份

`.docx` 分为两类：

1. **模板类 `.docx`**
   - 例如：`source_prd_template.docx`
   - 例如：`prd_template_reusable.docx`
   - 属于模板资产，不是正文产物

2. **交付类 `.docx`**
   - 由冻结后的 Markdown 生成
   - 用于正式交付、正式审阅或正式归档

### 6.2 `.docx` 的目录归属

正式 `.docx` 的建议目录为：

```text
docs/docx/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.docx
```

示例：

```text
docs/docx/产品需求管理流程规范/产品需求管理流程规范_v1.8_20260509.docx
docs/docx/文档仓库提交规范/文档仓库提交规范_v1.1_20260509.docx
```

### 6.3 临时渲染区

```text
render_current/
```

该目录只用于：

- 临时渲染
- 版式预览
- 转换检查

它不是正式归档区，不应作为长期存放位置。

### 6.4 `.docx` 与 Markdown 的强绑定

正式交付 `.docx` 必须同时满足：

- 有对应的 Markdown 冻结稿
- 版本号与 Markdown 快照一致
- 日期一致或可解释
- 文件名可互相检索
- 留有绑定记录

### 6.5 `.docx` 的版本规则

正式交付 `.docx` 的版本号必须与对应 Markdown 快照完全一致，不得单独跳号。

### 6.6 `.docx` 是否进入版本体系

推荐规则如下：

- Markdown 快照进入 `docs/versions/<文档名>/`
- 正式交付 `.docx` 进入 `docs/docx/<文档名>/`
- 两者通过绑定记录保持一一对应

也就是说，`.docx` 不进 Markdown 快照目录，但必须进入自己的正式交付目录。

### 6.7 绑定记录

每个正式 `.docx` 都应有一个绑定记录，至少写明：

- 对应 Markdown 快照路径
- 对应版本号
- 对应日期
- 生成来源
- 生成人
- 复核人

绑定记录的正式载体只有一个：

- 同目录的 `binding.md`

正式归档说明文件可以保留一份摘要或镜像说明，但不作为唯一正式载体。

## 7. 文档仓库提交协作

### 7.1 Git 角色

Git 负责：

- 仓库级审计
- 提交记录
- 分支历史
- 标签发布
- 回滚恢复

### 7.2 Git 不负责什么

Git 不负责：

- 代替会话记忆沉淀
- 代替 Markdown 冻结
- 代替 `.docx` 绑定关系
- 代替总入口导航

### 7.3 提交前置条件

正式提交前必须满足：

- 当前会话记录已更新
- 需要时已更新总索引
- 工作分支已创建或已切换
- Markdown 已冻结
- 快照已生成
- `.docx` 如属正式交付件，绑定关系已确认

## 8. 迁移策略

### 8.1 第一阶段：兼容

- 保留旧平铺快照
- 新增分层目录快照
- 总入口和提交规范只写新口径

### 8.2 第二阶段：冻结旧口径

- 旧平铺目录不再新增
- 所有新示例、脚本和说明改用分层目录
- 旧路径只用于历史引用

### 8.3 第三阶段：统一新口径

- 所有正式文档默认使用分层目录
- 所有正式 `.docx` 默认使用独立交付目录
- 总入口只保留导航，不再扩展规则

## 10. 最终状态

如果本方案落地完成，工作流会变成：

1. 从 `docs/工作流总入口.md` 进入
2. 先遵循 `AGENTS.md` 和会话记忆规则
3. 按主流程文档完成 Markdown 冻结
4. 生成对应分层快照
5. 如有正式交付 `.docx`，生成并绑定到独立目录
6. 进入 Git 提交和标签发布
7. 保留回滚链路和历史引用

这样可以同时满足：

- 总入口清晰
- 权威文档不打架
- 快照口径统一
- `.docx` 有明确归属
- 历史可追溯
- 回滚可执行

## 11. 结论

这套方案的关键不是再加规则，而是把每一层的职责锁死：

- `AGENTS.md` 和会话记忆规则管行为入口
- 总入口只做导航
- 主流程文档管正文
- 产物管理规则管文档对象
- 提交规范管 Git
- 快照目录统一为分层结构
- `.docx` 通过独立目录和绑定记录纳管

只要这三件事定死：

1. 总入口只导航
2. 快照目录只用分层口径
3. `.docx` 独立目录且强绑定 Markdown

整套链路就能真正闭环。

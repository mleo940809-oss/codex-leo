# `.docx` 产物链路说明

**版本**：V1.0  
**状态**：说明页  
**用途**：仅说明 `.docx` 的生成、绑定、留档和目录归属链路，不定义正文规则。

## 1. 作用

`.docx` 不是正文源，而是由冻结后的 Markdown 派生出来的正式交付件或正式归档件。

本说明只定义链路，不替代以下权威文档：

- [产品需求管理流程规范.md](/E:/Codex/New_rules/docs/产品需求管理流程规范.md)
- [工作产出物管理规则.md](/E:/Codex/New_rules/docs/工作产出物管理规则.md)
- [文档仓库提交规范.md](/E:/Codex/New_rules/docs/文档仓库提交规范.md)

## 2. 文件分类

### 2.1 模板类 `.docx`

- `source_prd_template.docx`
- `prd_template_reusable.docx`

模板类文件用于生成 PRD 和相关正式文档，不作为正文编辑源。

### 2.2 交付类 `.docx`

交付类 `.docx` 由冻结后的 Markdown 生成，用于正式交付、正式审阅或正式归档。

## 3. 生成顺序

正式 `.docx` 的推荐生成顺序如下：

1. 完成 Markdown 内容编写
2. 按主流程完成评审与冻结
3. 先通过 PRD 冻结前门禁，再进入 `.docx` 生成候选
4. 生成临时渲染文件到 `render_current/`
5. 检查版式与内容一致性
6. 输出正式 `.docx`
7. 更新绑定记录
8. 将正式 `.docx` 与绑定记录同步纳入 Git

### 3.1 PRD 冻结前门禁

如果 `.docx` 对应的是 PRD、高保真原型或交付包，正式生成前必须先满足以下 4 个门禁：

1. 完成 `PRD-原型一致性矩阵`
2. 完成 `PRD-原型一致性门禁`
3. 完成 `高保真原型可交互门禁`
4. 完成 `原型交互验收` 和 `需求交付包输出`

这 4 个门禁的具体定义与验收标准分别以：

- [PRD工作流复用模板.md](/E:/Codex/New_rules/docs/PRD工作流复用模板.md)
- [产品需求管理流程规范.md](/E:/Codex/New_rules/docs/产品需求管理流程规范.md)
- [流程执行技能附录.md](/E:/Codex/New_rules/docs/流程执行技能附录.md)

为准。

## 4. 目录归属

### 4.1 临时渲染区

```text
render_current/
```

该目录只用于临时渲染、预览和校验，不作为正式归档区。

### 4.2 正式交付区

```text
docs/docx/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.docx
```

示例：

```text
docs/docx/产品需求管理流程规范/产品需求管理流程规范_v1.8_20260509.docx
docs/docx/文档仓库提交规范/文档仓库提交规范_v1.1_20260509.docx
```

正式交付 `.docx` 只落在这个目录下，不进入 Markdown 快照目录。

## 5. 与 Markdown 的对应关系

正式交付 `.docx` 必须满足以下条件：

- 对应一个冻结后的 Markdown 快照
- 文件名版本号与 Markdown 快照版本号一致
- 日期可一致或可解释
- 可通过文件名和绑定记录互相检索

`.docx` 与 Markdown 的关系是 **一一对应**，不能一份 `.docx` 对应多个 Markdown 快照，也不能一个 Markdown 快照对应多个不同版本的正式 `.docx`。

## 6. 绑定记录

每个正式 `.docx` 都必须有一个绑定记录，且绑定记录的正式载体只有一个：

- `docs/docx/<文档名>/binding.md`

绑定记录至少包含：

- 对应 Markdown 快照路径
- 对应版本号
- 对应日期
- 生成来源
- 生成人
- 复核人

正式归档说明文件可以存在摘要或镜像，但不能与 `binding.md` 并列为正式载体。

## 7. 留档与发布

- 正式 `.docx` 发布前，必须先确认 Markdown 已冻结且快照已生成。
- 若 `.docx` 属于 PRD、原型或交付包，必须先通过上面的 5 项冻结前检查，再完成对应的原型绑定记录，再允许输出正式 `.docx`。
- 正式 `.docx` 与 `binding.md` 应在同一轮正式变更中进入 Git 历史。
- 原型绑定记录的正式载体为 `docs/prototype/<文档名>/binding.md`，并应与对应 PRD 冻结版本同轮留档。
- 若 `.docx` 仅用于中间转换或预览，可保留在 `render_current/`，但不视为正式留档。

## 8. 原型归档策略

正式原型在冻结后还应形成独立归档层，用于长期回读、审计和版本追溯。推荐归档路径如下：

```text
docs/prototype/<文档名>/archive/<文档名>_v<版本号>_<YYYYMMDD>/
```

每次正式冻结后，归档目录至少应保留：

- 归档清单 `archive-manifest.md`
- 原型活链接记录
- 原型版本号与对应 PRD 版本
- 源文件路径或导出文件路径
- 关键页面预览图 / 导出图
- 归档确认人和归档时间

归档层与 `binding.md` 的关系如下：

- `binding.md` 负责当前正式绑定
- `archive/` 负责冻结后留痕与长期保全
- 两者必须互相可追溯，但不能互相替代

归档层的更新原则：

- 每次正式冻结生成新的归档目录
- 归档目录一经生成不得覆盖旧版本
- 归档目录与正式 `.docx`、`binding.md` 同轮进入 Git 历史

## 9. 结论

`.docx` 的正式链路是：

Markdown 冻结稿 -> 临时渲染 -> 正式 `.docx` -> `binding.md` -> Git 留档

其中，Markdown 是正文源，`.docx` 是派生产物，`binding.md` 是唯一正式绑定记录载体。

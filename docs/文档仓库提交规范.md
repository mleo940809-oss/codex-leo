# 文档仓库提交规范

**版本**：V1.2  
**状态**：草案  
**适用对象**：`E:\Codex\New_rules` 内所有制度、流程、PRD、模板、产物治理和版本快照文档

## 0. 需求独立目录补充说明

0.1 `docs/versions/` 下的正式产出物，原则上应按“一个需求一个独立目录”管理。

0.2 同一需求产生的全部正式产出物，应集中放入该需求目录内，不得与其他需求混放。

0.3 需求目录下建议继续区分 `最新版本` 与 `历史版本`，以保证提交、回滚和快照管理清晰可追溯。

0.4 如该需求还包含原型、交付包、评审纪要等附属正式产物，建议一并放入该需求目录下的子目录中，不另起无关目录。

## 1. 目标

本规范用于把 Git 变成文档仓库的仓库级审计层，并与现有文档治理体系并行使用。目标是让每次修改都满足以下要求：

- 可追溯
- 可回滚
- 可审阅
- 可对比
- 可与文档版本和快照一一对应

## 2. 适用范围

本规范只管理 Git 层面的操作规则，包括：

- 分支创建
- 提交规范
- 快照提交
- 标签发布
- 合并门禁
- 回滚恢复

## 4. 标准执行顺序

每次正式修改都按以下顺序执行，不得跳步：

1. 判断本次修改是否属于正式修订
2. 生成对应文档快照
3. 创建工作分支
4. 修改正文
5. 校验正文与快照一致性
6. 提交 Git
7. 正式发布时打标签
8. 如有错误，按回滚规则恢复

## 5. 分支策略

### 5.1 分支原则

- `main` 只保留稳定、可发布版本。
- 正式修改必须先创建工作分支。
- 一个分支尽量只处理一个主题或一轮修订。

### 5.2 分支命名

建议使用以下格式：

```text
docs/<主题>
fix/<问题>
review/<轮次>
```

示例：

```powershell
git switch -c docs/prd-workflow-update
```

### 5.3 分支门禁

- 未创建分支，不得直接修改正式正文。
- 分支上若同时涉及多个主题，必须拆分后再提交。
- 不得把临时试验分支当正式发布分支。

## 6. 快照规则

### 6.1 什么时候生成快照

以下情况必须生成 `docs/versions/<文档名>/` 快照：

- 正式修订前
- 正式发布前
- 版本号递增时
- 需要保留稳定基线时

### 6.2 快照命名

推荐目录与命名格式：

```text
docs/versions/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.md
```

示例：

```text
docs/versions/产品需求管理流程规范/产品需求管理流程规范_v1.8_20260509.md
docs/versions/文档仓库提交规范/文档仓库提交规范_v1.1_20260509.md
```

### 6.3 快照要求

- 快照必须与生成时的正文内容一致。
- 快照是正式留档，不是临时备份。
- 快照不得覆盖历史文件，只能追加保存。
- 同一文档的快照必须集中保存在自己的独立子目录中，不得与其他文档混放。
- 任何旧平铺快照目录只允许只读兼容，不得作为新生成目标，也不得作为脚本默认输出目标。

### 6.4 快照与正文关系

- 主文档始终表示当前生效正文。
- 快照表示某一次正式发布或正式修订时的固定版本。
- 正文发生正式变化后，必须重新生成对应快照。

## 7. 提交规则

### 7.1 提交前检查

提交前必须确认：

- 本次改动是否属于同一主题
- 是否误改了无关文件
- 是否包含临时文件或生成物
- 是否已生成对应快照
- 正文与快照是否一致

推荐检查命令：

```powershell
git status
git diff
```

### 7.2 暂存原则

- 能精确指定文件时，优先按文件暂存。
- 只有在确认本次所有改动都要提交时，才使用 `git add .`。
- 不要把无法解释的杂项文件一起提交。

示例：

```powershell
git add docs/产品需求管理流程规范.md
git add docs/versions/产品需求管理流程规范/产品需求管理流程规范_v1.8_20260509.md
```

### 7.3 提交信息

提交信息要短、明确、可检索，推荐格式：

- `docs: update prd workflow`
- `docs: add review checklist`
- `docs: refresh version snapshot`
- `chore: update git rules`

要求：

- 说明这次提交做了什么
- 不要只写 `update`、`fix` 这种空泛词
- 一个提交尽量只表达一类变更

## 8. 标签与发布规则

### 8.1 标签用途

Git 标签用于标记仓库级正式发布点，不替代文档版本号。

建议标签命名：

```text
docs/<文档名>/v<版本号>
```

示例：

```text
docs/product-requirements-process/v1.8
```

### 8.2 发布时点

建议在以下情形打标签：

- 文档进入正式发布状态
- 形成可对外分发的稳定基线
- 需要后续回滚的关键节点

### 8.3 标签与快照关系

- 标签指向 Git 提交。
- 快照指向文档文件。
- 两者共同构成正式发布基线。

## 9. 版本号与文件名

### 9.1 文档版本号

文档正文版本号遵循主流程文档的版本号，例如 `V1.8`、`V1.9`。

### 9.2 快照版本号

快照文件名必须包含正文版本号和日期，必要时可追加修订标记，但不得省略版本号。

### 9.3 禁止行为

- 不得跳号
- 不得同名覆盖旧版本
- 不得把草稿直接命名为正式版本
- 不得在版本号里混入模糊词，例如“最终版”“新版”“优化版”

## 10. 回滚规则

### 10.1 回滚优先级

回滚时优先级如下：

1. 最近一次稳定 Git 标签
2. 最近一次正式快照
3. 最近一次可解释的提交

### 10.2 回滚原则

- 单文件误改：优先恢复主文档，再补齐快照。
- 版本内容错误：先恢复快照，再重新发布。
- 仓库级错误：以标签为基准回退。
- 不要直接对历史文件做覆盖式修补，必须保留痕迹。

### 10.3 回滚记录

每次回滚都应记录：

- 回滚原因
- 回滚对象
- 回滚来源
- 执行人
- 影响范围

## 11. 审阅与合并

### 11.1 审阅重点

审阅重点不是文字好不好看，而是：

- 是否改变流程口径
- 是否影响责任边界
- 是否影响版本规则
- 是否影响快照一致性

### 11.2 合并门禁

合并到 `main` 前必须确认：

- 主文档与快照一致
- 版本号已递增
- 变更理由已记录
- 没有未解释的临时文件

### 11.3 禁止事项

- 禁止只改主文档不留快照
- 禁止只留快照不提交 Git
- 禁止正文和快照版本号不一致
- 禁止把草稿当正式版合并

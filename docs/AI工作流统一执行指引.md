# AI 工作流统一执行指引

**版本**：V1.0  
**状态**：现行统一规则  
**适用范围**：`E:\Codex\New_rules` 内所有文档评审、PRD 产出或改写、产品需求管理、产物留档、原型绑定、`.docx` 交付、Git 留痕和会话记忆任务。  
**目标**：用一个可执行入口替代分散规则，减少漏读、跳步、模板混用和口头完成。

---

## 1. 规则优先级

1. 用户在当前对话中明确提出的要求。
2. `AGENTS.md`。
3. 本文件。
4. PRD 模板与专项产物模板。
5. 通用技能、工具说明和默认行为。

若规则冲突，优先采用更接近当前任务、且更具体的规则；仍无法消解时，先停止并向用户确认。

---

## 2. 每次任务的唯一主线

任何任务都按以下顺序执行：

1. 判断任务类型。
2. 判断当前阶段。
3. 选择唯一主路径。
4. 读取本文件中对应章节和必要模板。
5. 执行任务。
6. 做门禁检查。
7. 做版本、绑定、归档或留痕动作。
8. 输出结果。

禁止事项：

- 不得同时混跑多条主路径。
- 不得把草稿当正式交付。
- 不得把前期稿和正式稿混在同一文件反复覆盖。
- 不得跳过门禁、版本、绑定、归档或确认。
- 不得只做口头判断而不落到可追踪产物。

---

## 3. 任务分类

每次先选一个主类目，再处理附属事项：

| 主类目 | 适用任务 | 主路径 |
|---|---|---|
| 文档评审 | 审查制度、流程、PRD、交付包、模板 | 先找遗漏、矛盾、歧义、不可执行点、不可测试点、风险点和版本冲突 |
| PRD 产出或改写 | 新建 PRD、改 PRD、整理需求、冻结交付 | 按阶段选择前期模板或正式模板 |
| 产品需求管理 | 需求受理、初筛、分析、评审、冻结、交付、变更 | 按需求节点推进，节点未过不得流转 |
| 原型绑定或归档 | 高保真原型、交互原型、Figma/HTML 原型留档 | 先绑定，再归档，活链接和源文件必须齐全 |
| `.docx` 交付 | 生成或留档 Word 交付件 | Markdown 冻结后再派生 `.docx` |
| Git 提交或版本留档 | 快照、分支、提交、标签、回滚 | 先快照，再改正文，再提交 |
| 会话记忆沉淀 | 跨会话延续、上下文压缩、决策沉淀 | 持续写入单一会话记录 |
| 其他普通任务 | 不属于以上类型的协作任务 | 仍需判断阶段、验证结果、说明留痕边界 |

---

## 4. 阶段判断

| 阶段 | 定义 | 允许动作 | 禁止动作 |
|---|---|---|---|
| 探索 | 需求受理、问题定义、范围收敛、方案草案 | 澄清、分析、草案、待确认项 | 当作正式交付、冻结、发布 |
| 正式 | 正式评审、正式 PRD、研发交付准备 | 使用正式模板、补齐附件、评审确认 | 继续沿用前期模板 |
| 冻结 | 范围、版本、原型和交付口径已确认 | 按冻结版本交付，变更走审批 | 私自改正文、覆盖旧版本 |
| 归档 | 完成留痕、绑定、快照和长期保存 | 归档、绑定、回读、审计 | 随意改归档件 |

统一原则：

- 先验证，再判断。
- 先门禁，再流转。
- 先冻结，再交付。
- 先留痕，再覆盖。
- 先绑定，再归档。

## 5. 文档评审路径

评审时优先看问题，不先看修辞。

必须检查：

- 是否有遗漏。
- 是否有矛盾。
- 是否有歧义。
- 是否存在不可执行点。
- 是否存在不可测试点。
- 是否存在风险点。
- 是否存在版本、路径、责任或口径冲突。

输出要求：

- 评审结论必须落到文档或可执行修改建议中。
- 若对象是 PRD 或 PRD 流程文档，必须额外检查 PRD 阶段、模板、原型、交付包和冻结门禁。
- 不得只说“看起来没问题”，必须说明检查过的范围和残余风险。

## 6. 产品需求管理主流程

产品需求从受理到交付必须经过以下节点：

1. 需求受理。
2. 需求初筛与分级。
3. 需求分析。
4. 方案设计与评审。
5. 需求确认与冻结。
6. 需求交付包输出。
7. 紧急需求特批通道，仅用于符合条件的紧急事项。

### 6.1 基础原则

- 所有需求必须先登记，再进入后续流程。
- 未登记的需求不得进入分析。
- 未完成分级，不得进入需求分析。
- 未完成需求分析，不得进入方案设计。
- 没有通过方案评审，不得进入需求冻结。
- 未完成确认与冻结，不得输出交付包。
- 未完成交付包，不算流程完成。
- 冻结后变更必须走正式变更流程。

### 6.2 责任模型

每个节点必须明确：

- 主责人：对节点产出负责。
- 校验人/确认人：用于登记门禁的信息完整性与真实性校验。
- 审批人：用于审批门禁，决定是否进入下一阶段。
- 参与人：提供专业判断、信息或评估。
- 知会人：了解结果但不参与决策。

登记门禁必须有主责人和校验人/确认人；审批门禁必须有主责人和审批人。缺少对应责任人时，不得进入下一阶段。

### 6.3 需求受理门禁

进入条件：

- 需求提出方明确。
- 业务负责人明确，或已指定临时责任人。
- 有基本业务背景和诉求描述。
- 有期望时间或时效要求。

输出物：

- 需求登记单。
- 需求编号。
- 初始责任归属记录。

未明确业务负责人的需求不受理，紧急、合规或高层指令类需求除外，但必须由产品负责人指定代理 owner，并在 1 个工作日内补齐正式责任链或授权记录。

### 6.4 初筛与分级门禁

必须判断：

- 是否属于产品职责范围。
- 是否与经营目标相关。
- 是否重复、低价值或可通过配置、培训、流程解决。
- 优先级和紧急度。
- 进入正式分析、暂缓、关闭或特批。

分级结论必须写明原因，不得跳过初筛直接进入方案设计。

### 6.5 需求分析门禁

分析输出至少包含：

- 现状描述。
- 问题定义。
- 目标定义。
- 用户或角色范围。
- 数据依据。
- 影响范围。
- 风险点。
- 候选方向。

没有数据依据的结论必须标注为假设。没有问题定义，不得进入方案设计。

### 6.6 方案设计与评审门禁

方案必须包含：

- 方案说明。
- 至少一个备选方案对比。
- 成本、收益、风险、依赖和可落地性评估。
- 风险清单。
- 资源评估。
- 评审纪要。

评审不能只有讨论，没有决策。方案必须说明“不做什么”。

### 6.7 确认与冻结门禁

冻结内容必须包含：

- 业务目标。
- 功能范围。
- 核心流程。
- 页面或原型。
- 字段定义。
- 规则定义。
- 异常场景。
- 验收标准。

冻结前必须清零关键待定项和关键争议。冻结后原则上不改范围；如需修改，必须走变更审批。

### 6.8 交付包门禁

交付包必须满足：

- 与冻结版本一致。
- 列出完整输出物。
- 可追溯到需求编号、冻结版本和确认记录。
- 验收标准可判定，不能只写“已确认”。
- 交付包内每项必交付输出物都能在模板中找到对应位置。

缺少任一必交付输出物，交付包视为不完整，不能关闭该节点。

### 6.9 紧急需求特批

可走特批的场景：

- 门店经营事故。
- 核心系统异常。
- 监管或合规要求。
- 重大促销活动前临时调整。
- 高层临时指令。

特批规则：

- 特批不能替代正式流程。
- 不能取消关键审批，只能压缩流程时间。
- 必须说明特批原因、影响范围和处理时效。
- 事后 3 个工作日内补齐正式需求材料。
- 必须复盘，不得长期占用特批通道。

### 6.10 冻结后变更

触发条件：

- 业务目标变化。
- 范围新增或删除。
- 规则口径变化。
- 页面或字段变化。
- 依赖条件变化。

变更必须记录：

- 变更提出人。
- 变更原因。
- 变更影响范围。
- 变更审批人。
- 归档执行人。
- 变更前后版本。

未经过变更评审，不得修改冻结内容。

### 6.11 时限与升级

默认以 1 个工作日内响应为基准。响应不等于完成，必须分别记录。

常规时限：

| 节点 | 响应时限 | 完成时限 |
|---|---|---|
| 需求受理 | 1 个工作日内确认接单 | 1 个工作日内完成登记 |
| 需求初筛与分级 | 1 个工作日内开始判断 | 2 个工作日内完成分级 |
| 需求分析 | 1 个工作日内完成复杂度初判和排期说明 | 简单需求 3 个工作日内，复杂需求不超过 5 个工作日并说明原因 |
| 方案设计与评审 | 评审材料提前 1 个工作日发出 | 评审会后 2 个工作日内形成结论 |
| 需求确认与冻结 | 1 个工作日内确认是否进入冻结 | 2 个工作日内完成确认 |
| 需求交付包输出 | 1 个工作日内确认交付包缺口 | 2 个工作日内完成 |

节点超时必须升级，不能静默拖延。任何超时都必须记录原因。

### 6.12 决策与冲突裁定

- 冲突必须裁定，不能搁置不决。
- 裁定结果必须记录在案，不得口头放行。
- 合规、监管、数据安全红线由合规负责人优先裁定。
- 测试不可验收时，必须回到需求冻结阶段补齐标准。
- 多部门争议由产品负责人协调，必要时升级。

## 7. PRD 路径

PRD 任务必须按阶段选择模板。

| 阶段 | 使用文件 | 适用场景 |
|---|---|---|
| 前期探索 | `docs/PRD工作流复用模板.md` | 需求受理、需求探讨、问题定义、范围收敛、方案草案 |
| 正式交付 | `docs/standard-prd-template.md` | 正式评审、需求冻结、研发交付、测试验收、最终归档 |

硬规则：

- 前期稿和正式稿不得混用同一文件反复覆盖。
- 前期稿允许保留待确认、待定、备选方案；正式交付稿不得长期保留未确认占位。
- 进入正式评审、冻结或交付阶段，必须切换到正式模板。
- 正式 PRD 必须可追踪、可验证、可冻结、可交付。
- 任何功能点都要能回到页面、状态、交互、规则和异常。

### 7.1 正式 PRD 图示硬性要求

以下章节必须以图形化方式输出，不得只用纯文字段落替代：

- 1.4 应用架构。
- 1.5.1 功能清单，使用思维导图形式。
- 1.5.3 整体流程图。
- 2.1 角色用例图。
- 2.1.1.2.1 角色用例图。
- 2.1.1.2.2 产品流程图。
- 2.1.1.6 原型图 / UI 界面。

每张图必须同时提供：

- 图文件。
- 可编辑源文件。
- 必要图示说明。

### 7.2 功能需求拆解规则

正式 PRD 中：

- 每个一级功能模块必须拆到页面级或独立功能点。
- 每个页面级功能点必须拆到用户可执行动作。
- 每个动作必须说明触发条件、系统处理、成功结果和异常提示。
- 每个页面必须包含功能描述、用户故事、目标用户、前置条件、后置条件、功能逻辑、动作级说明、字段说明、业务规则、权限规则、状态流转、异常情况、埋点/日志和验收标准。

动作级说明固定格式：

| 动作名称 | 触发条件 | 系统处理 | 成功结果 | 异常提示 |
|---|---|---|---|---|
| 点击 `[按钮名称]` | 权限、状态、字段、业务条件 | 校验、保存、跳转、弹窗、状态变更、写日志、发起审批 | 页面反馈、数据变化、状态变化、输出结果 | 失败原因和提示文案 |

### 7.3 PRD 冻结前门禁

进入正式评审、冻结或交付前，必须确认：

- PRD-原型一致性矩阵已完成。
- PRD-原型一致性门禁已通过。
- 高保真原型可交互门禁已通过。
- 原型交互验收已完成。
- 需求交付包输出已完成。
- 原型绑定记录已完成。

少一项，都不能按正式交付推进。

### 7.4 PRD-原型一致性矩阵

矩阵为冻结前硬门禁。每个功能点、场景、规则和异常都必须在原型中找到对应页面、状态和交互。

| 功能点 / 场景 | 原型页面 / 路径 | 关键状态 | 关键交互 | 关联规则 / 异常 | 是否已覆盖 |
|---|---|---|---|---|---|
| 待填写 | 待填写 | 待填写 | 待填写 | 待填写 | 是 / 否 |

没有映射上的需求描述，不得进入冻结。若原型页面与 PRD 描述不一致，必须先修正再进入交付包关闭。

### 7.5 统一交付标准

所有正式需求交付物必须至少具备：

- 唯一需求编号。
- 冻结版本号。
- 明确业务负责人。
- 明确产品主责人。
- 评审结论。
- 范围边界。
- 原型活链接。
- PRD-原型一致性矩阵。
- 原型交互验收记录。
- 异常场景说明。
- 验收标准。
- 版本控制记录。

缺少任一项，视为交付不完整。

## 8. 原型绑定与归档

正式原型必须可点击、可验证、可回溯。不接受仅有截图、静态导出或录屏的高保真原型。

固定路径：

```text
docs/prototype/<文档名>/binding.md
docs/prototype/<文档名>/archive/<文档名>_v<版本号>_<YYYYMMDD>/
```

路径职责：

- `binding.md`：当前正式绑定记录，只保留一份。
- `archive/`：冻结后的历史归档目录，每次正式冻结新增一版。
- `render_current/`：仅用于临时渲染和预览，不视为正式留档。

### 8.1 绑定记录

正式原型必须先写 `binding.md`，再生成归档目录。

`binding.md` 至少包含：

- 原型活链接。
- 对应 PRD 版本。
- 原型范围。
- 原型版本或页面范围。
- 源文件路径。
- 确认人。
- 确认时间。
- 留档结果。

没有原型绑定记录，不得进入交付确认或冻结。

### 8.2 归档内容

每次正式归档至少保留：

- `archive-manifest.md`。
- 原型活链接。
- 对应 PRD 冻结版本。
- 原型版本号或页面范围。
- 源文件路径。
- 关键页面预览图或导出图。
- 归档确认人和归档时间。

归档目录一经生成不得覆盖旧版本。正式原型、`binding.md`、归档目录必须同轮进入 Git 历史。

### 8.3 原型禁止事项

- 禁止把临时预览稿当正式归档。
- 禁止只留截图而没有源文件路径。
- 禁止没有 `binding.md` 就直接归档。
- 禁止冻结后覆盖旧归档目录。
- 禁止让原型归档脱离对应 PRD 版本。

## 9. `.docx` 交付链路

`.docx` 不是正文源，而是冻结后的 Markdown 派生产物。

正式生成顺序：

1. 完成 Markdown 内容编写。
2. 完成评审与冻结。
3. 通过 PRD 冻结前门禁。
4. 生成临时渲染文件到 `render_current/`。
5. 检查版式与内容一致性。
6. 输出正式 `.docx`。
7. 更新绑定记录。
8. 将正式 `.docx` 与绑定记录同步纳入 Git。

正式交付路径：

```text
docs/docx/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.docx
docs/docx/<文档名>/binding.md
```

硬规则：

- `.docx` 必须对应一个冻结后的 Markdown 快照。
- 文件名版本号必须与 Markdown 快照版本号一致。
- `.docx` 与 Markdown 必须一一对应。
- 不允许一个 `.docx` 对应多个 Markdown。
- 不允许一个 Markdown 对应多个正式 `.docx`。
- 正式 `.docx` 与 `binding.md` 应在同一轮正式变更中进入 Git 历史。

`binding.md` 至少包含：

- 对应 Markdown 快照路径。
- 对应版本号。
- 对应日期。
- 生成来源。
- 生成人。
- 复核人。

## 10. 工作产出物管理

正式产出物包括但不限于：

- 需求登记单。
- 需求分级结果。
- 需求分析稿。
- 方案说明。
- 评审纪要。
- 冻结版需求说明。
- 交付包。
- 变更单。
- 复盘记录。
- 版本快照。
- 历史版本文件。
- 与主文档绑定的附件文件。
- 原型绑定记录。

不自动视为正式产出物的内容：

- 口头讨论。
- 聊天记录。
- 临时截图。
- 临时表格。
- 未纳入流程的个人草稿。
- 仅供参考的中间材料。

### 10.1 责任链

每个正式产出物必须明确：

- 创建人。
- 内容负责人。
- 归档执行人。
- 最终确认人。

同一人承担多个角色时，必须在记录中注明原因，不得默认视为流程合规。

### 10.2 标识与版本

正式产出物必须具备：

- 唯一编号。
- 需求编号关联。
- 节点编号关联。
- 版本号。
- 归档日期。

建议命名格式：

```text
<产出物名称>_<需求编号>_<版本号>_<YYYYMMDD>
```

正式产出物版本号必须递增管理，不得在正式版本上直接覆盖修改而不留痕。

### 10.3 主文档与附件一致性

原型、流程图、字段表、规则表、验收标准等附件必须与主文档版本绑定，且版本一致。

若主文档与附件版本不一致：

1. 立即暂停继续流转。
2. 以冻结版本作为唯一基线核对。
3. 同步修正主文档与附件。
4. 重新校验一致性。
5. 校验通过前，不得进入下一流程节点。

任何版本不一致都视为待纠错状态，不视为有效正式版本。

### 10.4 修改与变更

任何正式产出物在修改前，必须先生成历史快照，再修改正文。

冻结后的正式产出物如需修改，必须先发起变更单，经审批后方可修改。

禁止行为：

- 未备份直接覆盖正式版本。
- 以口头同意替代变更记录。
- 以聊天结论替代正式版本。
- 未留痕删除旧版本。
- 在附件版本未同步的情况下单独修改主文档。

纯格式修正仅限不改变业务含义、字段口径、流程顺序、责任归属、验收标准和依赖关系的修正。无法明确证明不影响业务含义时，必须走变更单。

### 10.5 需求独立目录

每个新需求、主题或独立工作项，原则上必须在 `docs/versions/` 下建立独立目录：

```text
docs/versions/<需求名称>/
  <当前最新版本文件>
  历史版本/
    <页面主题>/
      <该页面主题的历史版本文件>
```

同一需求下的全部正式产出物必须集中存放于同一需求目录内，不得分散到多个无关目录，也不得与其他需求混放。

历史版本必须先按页面主题分类，再放入对应版本文件。页面主题目录名称应与正式文档主题一致，避免使用“其他”“misc”“temp”等模糊目录名。

### 10.6 状态迁移

正式产出物标准状态：

```text
草稿 -> 评审中 -> 冻结 -> 正式发布 -> 归档 -> 废弃
```

规则：

- 草稿可进入评审。
- 评审通过后方可进入冻结。
- 冻结后方可进入正式发布。
- 正式发布后方可进入归档。
- 归档后原则上不再编辑。
- 废弃件不得作为当前版本使用。

废弃件必须保留，不得直接删除。

### 10.7 正式产物完成门禁

任何正式产出物必须同时满足：

- 有唯一编号。
- 有版本号。
- 有创建人。
- 有内容负责人。
- 有归档执行人。
- 有最终确认人。
- 有历史快照。
- 有可追溯路径。
- 有附件一致性。
- 有变更记录。

缺少任一项，不得视为正式产出物完成。

## 11. Git 与仓库留痕

Git 是文档仓库的审计层，不替代文档版本、快照和归档规则。

每次正式修改按以下顺序执行：

1. 判断本次修改是否属于正式修订。
2. 生成对应文档快照。
3. 创建工作分支。
4. 修改正文。
5. 校验正文与快照一致性。
6. 提交 Git。
7. 正式发布时打标签。
8. 如有错误，按回滚规则恢复。

### 11.1 分支规则

- `main` 只保留稳定、可发布版本。
- 正式修改必须先创建工作分支。
- 一个分支尽量只处理一个主题或一轮修订。
- 未创建分支，不得直接修改正式正文。
- 不得把临时试验分支当正式发布分支。

建议分支命名：

```text
docs/<主题>
fix/<问题>
review/<轮次>
```

### 11.2 快照规则

以下情况必须生成 `docs/versions/<文档名>/` 快照：

- 正式修订前。
- 正式发布前。
- 版本号递增时。
- 需要保留稳定基线时。

快照命名：

```text
docs/versions/<文档名>/<文档名>_v<版本号>_<YYYYMMDD>.md
```

快照必须与生成时的正文内容一致。快照不得覆盖历史文件，只能追加保存。

### 11.3 提交规则

提交前必须确认：

- 本次改动是否属于同一主题。
- 是否误改无关文件。
- 是否包含临时文件或生成物。
- 是否已生成对应快照。
- 正文与快照是否一致。

暂存原则：

- 能精确指定文件时，优先按文件暂存。
- 只有确认本次所有改动都要提交时，才使用 `git add .`。
- 不要把无法解释的杂项文件一起提交。

提交信息要短、明确、可检索，例如：

```text
docs: update prd workflow
docs: add review checklist
docs: refresh version snapshot
chore: update git rules
```

### 11.4 标签与回滚

Git 标签用于标记仓库级正式发布点，不替代文档版本号。

标签建议：

```text
docs/<文档名>/v<版本号>
```

回滚优先级：

1. 最近一次稳定 Git 标签。
2. 最近一次正式快照。
3. 最近一次可解释的提交。

每次回滚都应记录原因、对象、来源、执行人和影响范围。

### 11.5 合并门禁

合并到 `main` 前必须确认：

- 主文档与快照一致。
- 版本号已递增。
- 变更理由已记录。
- 没有未解释的临时文件。

禁止：

- 只改主文档不留快照。
- 只留快照不提交 Git。
- 正文和快照版本号不一致。
- 把草稿当正式版合并。

## 12. 会话记忆

涉及跨会话协作、长任务延续、上下文压缩风险或决策沉淀时，必须持续沉淀会话记录。

强制规则：

- 禁止只在会话结束时才总结。
- 只要出现压缩前兆，必须先总结，再继续推进当前会话。
- 每个会话必须对应一个唯一的会话记录。
- 会话记录必须持续更新，不得只做一次性归档后不再维护。
- 每次形成新的关键结论、决定、待办、风险或未决问题，都要同步写入会话记录。
- 执行会话总结时，必须产出对应的会话记录文档，不得只在聊天窗口内完成总结。
- 需要沉淀时优先使用 `notion-knowledge-capture`。

触发条件：

- 背景剩余空间预计降至 35% 或更低。
- 背景信息窗口明显缩小，接近自动压缩风险。
- 系统提示背景信息将被压缩或已开始压缩。
- 当前会话出现较多主题切换，后续回忆成本明显上升。
- 关键决策已经形成，但尚未落到可检索记录中。
- 当前会话预计还会继续，但上下文保留风险已高于可接受阈值。

会话记录至少包含：

- 会话主题。
- 会话日期。
- 当前目标。
- 已确认事项。
- 已做决定。
- 待办事项。
- 风险与限制。
- 未决问题。
- 下一步动作。
- 相关会话或相关主题的引用入口。

如果已经进入压缩阶段但尚未总结，必须优先补写最小可恢复摘要，再继续后续工作。

## 14. 最终自检

准备结束前，至少检查：

- 是否判断了任务类型。
- 是否判断了当前阶段。
- 是否只走了一条主路径。
- 是否选对模板。
- 是否完成对应门禁。
- 是否完成版本、绑定、归档或留痕动作。
- 是否能追溯到需求编号、版本、确认人和路径。
- 是否把结果落到文档或实际产物中。

一票否决项：

- 未判定任务类型。
- 模板选错。
- 前期稿和正式稿混在一起。
- 跳过门禁。
- 没有版本或留痕。
- 没有绑定或归档。
- 结果不可追溯。

最短执行口令：

**先分类，再定阶段；先读统一指引，再走唯一主路径；先过门禁，再做产物；最后留痕。**

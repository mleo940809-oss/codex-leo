# 产品需求管理流程规范

> 适用范围：产品部门内部，从需求输入、需求分析、方案评审、需求确认到需求交付包输出。

**版本**：V1.5  
**状态**：草案  
**适用对象**：产品、业务、设计、数据、运营、技术相关协作角色  
**目标**：建立统一、可追踪、可审批、可执行的产品需求落地流程，减少口头需求、反复变更和责任不清问题。

**本版修订重点**：补齐登记门禁与审批门禁的区分、登记校验的独立性、测试角色闭环、自检豁免条件收紧、角色命名统一、SLA 分类标准、响应与完成口径拆分、版本快照触发规则、节点强制技能执行规则、工作产出物管理规则。

---

## 1. 目的

本规范用于统一产品需求管理口径，确保每个需求都经过统一受理、规范分析、充分评审、明确确认和标准交付，避免需求在推进过程中出现以下问题：

- 入口不统一，导致需求散落在聊天、会议和口头沟通中
- 需求目标不清，分析不到位，直接进入方案设计
- 方案未评审，边做边改，反复返工
- 需求范围未冻结，执行过程中频繁变更
- 责任角色不清，出现问题后无法追责和复盘

---

## 2. 流程原则

1. **统一入口**：所有需求必须先登记，再进入后续流程。
2. **先分析后设计**：先把问题定义清楚，再讨论解决方案。
3. **关键节点强审批**：分级、分析结论、方案评审、需求冻结、交付包输出均需明确审批。
4. **范围冻结**：确认后的需求原则上不再变更，变更必须走审批。
5. **责任明确**：每个节点必须明确主责人、审批人、参与人、知会人。
6. **技能强制执行**：每个节点到达时，必须按本规范指定的 skills 顺序执行，不得绕过、合并或跳过。
7. **例外可控**：紧急需求允许走特批通道，但必须事后补齐材料并复盘。

---

## 3. 角色定义

| 角色 | 定义 |
|---|---|
| 需求提出方 | 提出需求的业务部门、门店、运营或管理层人员 |
| 业务负责人 | 对业务目标、诉求真实性和业务结果负责的人 |
| 产品经理 | 需求流程主责人，负责收口、分析、组织评审和交付 |
| 产品负责人/产品总监 | 对需求优先级、资源投入和关键争议进行审批 |
| 数据分析/经营分析 | 提供数据依据、指标口径和效果验证建议 |
| 设计 | 提供交互、页面和体验方案建议 |
| 产品助理/登记专员 | 负责需求登记、信息校验、版本归档和快照留存 |
| 技术代表 | 提供技术可行性、实现成本和依赖风险判断 |
| 技术负责人 | 对技术方案、架构风险、排期可行性和技术裁定负责 |
| 测试代表/测试负责人 | 对验收标准、可测性、回归风险和测试裁定负责 |
| 合规负责人 | 对监管、法律、数据安全、内控与审计风险负责 |
| 运营/门店代表 | 提供一线业务场景、执行约束和落地反馈 |

---

## 4. 责任模型

每个节点必须明确以下四类责任：

- **主责人**：对该节点产出负责
- **校验人/确认人**：仅用于登记门禁节点，对信息完整性、真实性做独立校验，不承担审批职责
- **审批人**：仅用于审批门禁节点，对该节点是否可进入下一阶段拥有决定权
- **参与人**：提供专业判断、信息或评估
- **知会人**：需要了解结果，但不参与决策

登记门禁节点必须有主责人和校验人/确认人，但不要求审批人。审批门禁节点必须有主责人和审批人。若缺少对应责任人，则该节点不得进入下一阶段。登记门禁的校验人原则上应与主责人分离。

---

## 4.1 节点技能执行规则

1. 每个节点在到达时，必须先执行本节点指定的 skill，再进入本节点产出和审批动作。
2. 若某节点配置了多个 skills，必须按“主 skill -> 辅 skill”的顺序执行。
3. 本规范中列出的 skills 为强制执行项，不是建议项，不得因熟练度、时间紧张或人员不足而绕过。
4. 如确实因人员配置不足无法执行辅助 skill，必须记录原因并由产品负责人批准临时替代方案；替代方案不得取消主 skill。
5. 节点输出物必须能追溯到已执行的 skill 名称和结果记录。

---

## 5. 流程总览

| 节点 | 名称 | 目标 | 是否强审批 |
|---|---|---|---|
| 1 | 需求受理（登记门禁） | 统一收口，建立需求编号和归属 | 否 |
| 2 | 需求初筛与分级 | 判断是否受理、是否紧急、是否值得做 | 是 |
| 3 | 需求分析 | 明确问题、目标、范围和约束 | 是 |
| 4 | 方案设计与评审 | 输出可执行方案并完成评审决策 | 是 |
| 5 | 需求确认与冻结 | 锁定范围，防止后续反复变更 | 是 |
| 6 | 需求交付包输出 | 形成标准化落地材料 | 是 |
| 7 | 紧急需求特批通道 | 处理突发经营问题或高优先级特批事项 | 是 |

## 6. 节点定义

### 6.1 需求受理

**目标**：所有需求统一进入产品需求池，禁止口头直推和私下插单。

**必用Skills**
- 主 skill：`notion:notion-knowledge-capture`
- 辅 skill：`slack:slack-reply-drafting`

**具体工作**
- 将口头、聊天、邮件、会议中的原始需求转成结构化登记内容
- 补全需求名称、来源、提出人、业务负责人、背景、诉求、时效
- 形成统一需求编号和登记单
- 将需补充的信息整理成可回传给提出方的追问清单

**强制规则**
- 未执行上述 skills，不得完成需求受理
- 未形成登记单，不得进入需求初筛
- 不得跳过登记直接进入分析、评审或设计

**主责人**：产品经理  
**校验人/确认人**：优先由产品助理或指定登记角色担任；如人员配置受限，可由产品经理自检，但必须在登记单中标注“自检”  
**审批人**：无正式审批；该节点为登记门禁，不是审批门禁  
**参与人**：需求提出方、业务负责人  
**知会人**：相关业务线负责人

**进入条件**
- 需求提出方明确
- 业务负责人明确，或已指定临时责任人/代理 owner
- 有基本业务背景和诉求描述
- 有期望时间或时效要求

**管控动作**
- 记录需求名称、来源、提出人、业务负责人、背景、诉求、期望时间
- 生成需求编号
- 确认是否属于产品职责范围

**输出物**
- 需求登记单
- 需求编号
- 初始责任归属记录

**退出条件**
- 需求已登记
- 具备进入初筛的基础信息

**规则**
- 未登记的需求不得进入分析
- 未明确业务负责人的需求不受理，除非属于紧急、合规或高层指令类需求，并由产品负责人临时指定代理 owner 接管
- 紧急、合规或高层指令类需求进入后，产品经理必须在 1 个工作日内补齐正式业务 owner 或完成临时责任授权记录
- 若由产品经理自检受理信息，仅限以下情况之一：1）产品部门暂无产品助理/登记专员编制；2）当天因请假、出差、离岗导致登记角色无人可用。自检仅用于补齐登记信息，不替代门禁确认；连续自检不得超过 3 个工作日，且最迟应在 5 个工作日内补齐独立校验确认

---

### 6.2 需求初筛与分级

**目标**：判断需求是否值得做、急不急做、走哪条路径。

**必用Skills**
- 主 skill：`superpowers:brainstorming`
- 辅 skill：`superpowers:systematic-debugging`

**具体工作**
- 拆解问题边界、识别需求真实目标
- 判断需求价值、紧急度、重复性和可行性
- 对需求做初步分级和路径判断
- 找出隐藏前提、冲突点和无效需求

**强制规则**
- 未完成分级，不得进入需求分析
- 分级结论必须写明原因
- 不得跳过初筛直接进入方案设计

**主责人**：产品经理  
**审批人**：产品负责人/产品总监  
**参与人**：业务负责人、数据分析、运营代表  
**知会人**：相关干系人

**管控动作**
- 判断需求是否属于产品职责范围
- 判断是否与经营目标相关
- 判断是否重复、低价值或可通过配置/培训/流程解决
- 判断优先级和紧急度
- 决定进入正式分析、暂缓、关闭或特批

**输出物**
- 需求分级结果
- 优先级建议
- 处理路径建议

**退出条件**
- 完成分级
- 明确下一步路径

**规则**
- 分级必须写明原因
- 紧急需求不得直接跳过审批进入执行
- 低价值、重复、不可行需求可关闭或暂缓

---

### 6.3 需求分析

**目标**：把“业务诉求”转化为清晰的问题定义、目标定义和边界定义。

**必用Skills**
- 主 skill：`superpowers:writing-plans`
- 辅 skill：`notion:notion-spec-to-implementation`

**具体工作**
- 将需求拆成问题定义、目标定义、影响范围和约束条件
- 输出分析结论、候选方向和数据依据
- 把分析结果整理成后续可执行的计划型表达
- 为后续方案设计提供清晰边界

**强制规则**
- 未完成需求分析，不得进入方案设计
- 没有数据依据的结论必须标注为假设
- 分析阶段允许否决需求本身

**主责人**：产品经理  
**审批人**：业务负责人  
**参与人**：数据分析、门店代表、运营代表、设计  
**知会人**：产品负责人

**管控动作**
- 梳理现状流程
- 描述问题现象
- 分析根因
- 定义目标
- 确定影响范围
- 识别约束条件
- 提出可选方向

**分析输出应至少包含**
- 现状描述
- 问题定义
- 目标定义
- 用户/角色范围
- 数据依据
- 影响范围
- 风险点
- 候选方向

**输出物**
- 需求分析稿
- 问题定义结论
- 目标指标
- 场景说明
- 数据依据

**退出条件**
- 问题定义清晰
- 目标定义明确
- 业务负责人确认分析结论

**规则**
- 没有问题定义，不得进入方案设计
- 没有数据依据的结论必须标注为假设
- 分析阶段允许否决需求本身

---

### 6.4 方案设计与评审

**目标**：输出可执行方案，并判断该方案是否值得投入。

**必用Skills**
- 主 skill：`superpowers:receiving-code-review`
- 辅 skill：`superpowers:brainstorming`

**具体工作**
- 收集并评审业务、技术、测试、设计和数据反馈
- 对比备选方案，识别冲突与风险
- 裁定方案是否通过，或要求回到分析阶段重做
- 明确方案中“不做什么”

**强制规则**
- 评审前必须完成本节点 skill 执行
- 评审必须形成明确结论，不能只讨论
- 未通过评审，不得进入需求冻结

**主责人**：产品经理  
**审批人**：产品负责人/产品总监  
**参与人**：业务负责人、设计、技术代表、数据分析、运营代表  
**知会人**：相关部门负责人

**管控动作**
- 输出方案草案
- 对比至少一个备选方案
- 评估成本、收益、风险、依赖和可落地性
- 组织评审会
- 形成明确结论

**输出物**
- 方案说明
- 备选方案对比
- 风险清单
- 资源评估
- 评审纪要

**退出条件**
- 评审结论明确
- 推荐方案确定
- 关键风险和依赖被识别

**规则**
- 评审不能只有讨论，没有决策
- 没有通过评审，不得进入需求冻结
- 方案必须说明“不做什么”

---

### 6.5 需求确认与冻结

**目标**：锁定需求范围、口径和边界，防止后续反复改动。

**必用Skills**
- 主 skill：`superpowers:verification-before-completion`
- 辅 skill：`superpowers:executing-plans`

**具体工作**
- 核对范围、页面、字段、规则、异常场景和验收标准
- 确认需求冻结条件是否满足
- 检查是否还有待定项和未确认项
- 为后续执行提供冻结版基准

**强制规则**
- 未完成确认与冻结，不得输出交付包
- 冻结前必须完成所有关键争议确认
- 冻结后变更必须走正式变更流程

**主责人**：产品经理  
**审批人**：业务负责人 + 产品负责人/产品总监  
**参与人**：设计、技术代表、数据分析、运营代表  
**知会人**：后续执行相关人

**管控动作**
- 确认功能范围
- 确认页面、字段、规则、异常场景
- 确认优先级
- 确认待定项清零
- 冻结版本

**冻结内容**
- 业务目标
- 功能范围
- 核心流程
- 页面/原型
- 字段定义
- 规则定义
- 异常场景
- 验收标准

**输出物**
- 冻结版需求说明
- 确认记录
- 变更规则
- 待办项清单

**退出条件**
- 需求范围冻结
- 所有关键争议有结论

**规则**
- 冻结后原则上不改范围
- 如需变更，必须走变更审批

### 6.6 需求交付包输出

**目标**：输出标准化交付材料，支持后续执行团队直接使用。

**必用Skills**
- 主 skill：`documents:documents`
- 辅 skill：`notion:notion-knowledge-capture`

**交付包必须包含的输出物**
- PRD 正文
- 交付包清单
- 冻结/归档记录
- 验收标准
- 附件清单
- 依赖说明
- 交付确认记录

**具体工作**
- 生成标准化交付文档和附件
- 归档版本、编号和冻结记录
- 整理交付清单、验收标准和依赖说明
- 将知识沉淀为可复用文档资产
- 对照 `E:\Codex\New_rules\docs\PRD工作流复用模板.md` 核对输出结构

**强制规则**
- 未完成交付包，不算流程完成
- 交付包必须与冻结版本一致
- 缺少任一必交付输出物，交付包视为不完整，不能关闭该节点
- 验收标准必须可判定，不能只写“已确认”
- 交付包清单必须与冻结版本一一对应
- 没有文档化交付，不得进入关闭状态

**输出要求**
- 标准交付包
- 交付清单
- 交付确认记录

**退出条件**
- 交付包齐备
- 与冻结版本一致
- 已完成审批确认
- 交付包内的每项必交付输出物都能在模板中找到对应位置

**规则**
- 没有交付包，不算流程完成
- 交付包必须可追溯到需求编号和冻结版本

## 7. 紧急需求特批通道

### 7.1 适用场景

**必用Skills**
- 主 skill：`superpowers:systematic-debugging`
- 辅 skill：`superpowers:receiving-code-review`

**具体工作**
- 快速定位紧急问题根因
- 判断是否属于特批场景
- 评估风险、影响范围和最短处理路径
- 给出是否启动特批通道的判断

**强制规则**
- 未完成紧急性判断，不得直接执行特批
- 必须先判定问题性质，再进入特批流程

以下情形可走特批通道：

- 门店经营事故
- 核心系统异常
- 监管或合规要求
- 重大促销活动前临时调整
- 高层临时指令

**特殊规则**
- 紧急、合规、高层指令类需求可以先由产品负责人指定临时责任人/代理 owner 接管，不要求在受理时就具备自然业务 owner
- 临时责任人必须在需求登记单中显式记录，并在进入分析前补齐正式责任链或明确持续授权

### 7.2 责任角色

**必用Skills**
- 主 skill：`superpowers:receiving-code-review`
- 辅 skill：`superpowers:brainstorming`

**具体工作**
- 明确特批链路中的业务、技术、数据、运营参与方
- 识别冲突意见和裁定边界
- 形成特批责任分配

**强制规则**
- 未明确责任角色，不得进入特批执行
- 特批链路必须保留可追溯记录

**主责人**：产品经理  
**审批人**：产品负责人/业务负责人，必要时上升至更高层  
**参与人**：技术代表、运营代表、数据分析  
**知会人**：相关执行团队

### 7.3 管控规则

**必用Skills**
- 主 skill：`superpowers:systematic-debugging`
- 辅 skill：`verification-before-completion`

**具体工作**
- 检查特批原因、影响范围、处理时效和补齐责任是否落实
- 对特批过程进行事后校验
- 确认是否按时补齐正式材料

**强制规则**
- 特批不能替代正式流程
- 未补齐正式材料，不得关闭特批事项

- 必须说明特批原因
- 必须说明影响范围和处理时效
- 不能取消关键审批，只能压缩流程时间
- 事后 3 个工作日内补齐正式需求材料
- 必须复盘，不得长期占用特批通道

## 8. 变更管理规则

需求在冻结后如需变更，必须走变更流程。

**必用Skills**
- 主 skill：`superpowers:receiving-code-review`
- 辅 skill：`superpowers:writing-plans`

**具体工作**
- 审查变更请求是否影响范围、规则和依赖
- 评估变更收益、成本和风险
- 决定接受、拒绝或要求重做
- 把变更整理成可执行的修订计划

**强制规则**
- 未经过变更评审，不得修改冻结内容
- 所有变更必须可追溯

**变更触发条件**
- 业务目标变化
- 范围新增或删除
- 规则口径变化
- 页面或字段变化
- 依赖条件变化

**变更责任**
- **主责人**：产品经理
- **审批人**：业务负责人 + 产品负责人
- **参与人**：设计、技术代表、数据分析、运营代表

**变更要求**
- 变更原因必须记录
- 变更影响必须评估
- 变更前后版本必须可追溯
- 紧急变更同样需要审批

## 9. 时限与升级机制

为避免流程卡死，每个节点均设置**响应时限**、**完成时限**、提醒和升级路径。未特别说明时，默认以**1 个工作日内响应**为基准。

**必用Skills**
- 主 skill：`superpowers:executing-plans`
- 辅 skill：`superpowers:verification-before-completion`

**具体工作**
- 按节点时限推进事项
- 检查是否响应、是否完成、是否超时
- 触发提醒、升级和阻塞记录
- 验证节点是否按时完成

**强制规则**
- 节点超时必须升级，不能静默拖延
- 响应不等于完成，必须按口径分别记录

### 9.0 口径说明

- **响应时限**：指责任人收到需求后，确认已接单、已开始处理或已安排下一步动作的最长时间。
- **完成时限**：指该节点要求的输出物已经形成，并通过对应退出条件确认的最长时间。
- 响应不等于完成。当天响应、次日完成，属于符合规范；当天未响应但次日完成，不符合响应要求。

### 9.0.1 需求复杂度判定标准

需求分析阶段先由产品经理初判复杂度，再由技术负责人和业务负责人复核。

**简单需求**需同时满足以下条件：
- 单一业务场景
- 单系统或单流程调整
- 不涉及跨部门协同
- 不新增关键口径或复杂规则
- 不涉及权限、资金、合规、审计红线
- 不存在外部系统强依赖

**复杂需求**满足以下任一条件即可：
- 跨系统或跨流程
- 涉及两个及以上业务部门
- 存在外部系统依赖
- 涉及权限、资金、合规、审计、数据安全
- 需要新增或重构关键规则、口径或流程
- 需要较多异常场景或多角色协同

**裁定规则**
- 产品经理负责初判
- 技术负责人对技术复杂度和依赖复杂度复核
- 业务负责人对业务复杂度和影响范围复核
- 复杂度存在争议时，由产品负责人裁定

### 9.1 默认时限

| 节点 | 响应时限 | 完成时限 | 超时提醒 | 逾期升级 |
|---|---|---|---|---|
| 需求受理 | 1 个工作日内确认接单 | 1 个工作日内完成登记 | 当日提醒产品经理 | 超过 1 个工作日，升级至产品负责人 |
| 需求初筛与分级 | 1 个工作日内开始判断 | 2 个工作日内完成分级 | 第 2 天提醒产品经理和审批人 | 超过 2 个工作日，升级至产品负责人并标记阻塞原因 |
| 需求分析 | 1 个工作日内完成复杂度初判和排期说明 | 3 个工作日内完成简单需求；复杂需求不超过 5 个工作日并说明原因 | 第 3 天提醒主责人与业务负责人 | 超过时限，升级至产品负责人协调资源 |
| 方案设计与评审 | 评审材料提前 1 个工作日发出 | 评审会后 2 个工作日内形成结论 | 超时未反馈即提醒审批人 | 超过 2 个工作日未决策，升级至产品负责人裁定 |
| 需求确认与冻结 | 1 个工作日内确认是否进入冻结 | 2 个工作日内完成确认 | 第 2 天提醒相关审批人 | 超过 2 个工作日，升级至产品负责人和业务负责人联审 |
| 需求交付包输出 | 1 个工作日内确认交付包缺口 | 2 个工作日内完成 | 第 2 天提醒主责人 | 超过 2 个工作日，升级至产品负责人 |

### 9.2 升级路径

1. 节点负责人超时未响应，先由产品经理发起一次正式提醒。
2. 再超时一个工作日，升级至该节点审批人。
3. 仍未解决的，升级至产品负责人或产品总监协调。
4. 如涉及经营损失、合规风险或上线窗口，产品负责人可直接上升至更高管理层裁定。

### 9.3 SLA 说明

- 紧急需求不适用常规时限，但必须在受理时声明“特批时效”。
- 复杂需求可延长分析时限，但必须同步说明原因、预计完成时间和阻塞项。
- 任何超时都必须记录原因，不能以“大家都很忙”作为正式说明。

## 10. 决策与冲突裁定机制

需求评审必须有结果。出现冲突时，按以下规则裁定：

**必用Skills**
- 主 skill：`superpowers:receiving-code-review`
- 辅 skill：`superpowers:brainstorming`

**具体工作**
- 收集冲突意见并逐条归类
- 判断业务、技术、合规、测试之间的冲突边界
- 裁定谁说了算、谁升级、谁保留否决建议权

**强制规则**
- 冲突必须裁定，不能搁置不决
- 裁定结果必须记录在案，不得口头放行

### 10.1 裁定原则

- **业务目标冲突**：以业务负责人意见为主，产品负责人负责综合裁定
- **技术不可行或高风险**：技术负责人可提出不可行或需调整意见；若业务仍坚持推进，由产品负责人决定是否升级裁定
- **合规/监管风险**：合规负责人优先，涉及法律、监管、数据安全红线时具有否决权
- **测试不可验收**：测试代表/测试负责人对验收标准、可测性和回归风险有否决建议权；若标准不清，必须回到需求冻结阶段补齐
- **多业务方争抢优先级**：由产品负责人统一排序，必要时上升至业务管理层

### 10.2 冲突升级链路

1. 节点内先由主责人组织对齐
2. 对齐失败，由该节点审批人裁定
3. 审批人仍无法裁定时，升级至产品负责人
4. 涉及重大经营影响、预算冲突或合规红线时，升级至更高管理层或合规负责人

### 10.3 最终拍板规则

- 常规业务需求：产品负责人最终拍板
- 合规/监管类需求：合规意见优先
- 技术架构重大风险：技术负责人拥有否决建议权，必要时上升决策
- 多部门争议：产品负责人协调，业务负责人共同确认

## 14. 版本管理与历史备份

为保证文档修订可追溯、可回滚、可审计，所有正式文档修改必须遵守以下规则：

**必用Skills**
- 主 skill：`superpowers:finishing-a-development-branch`
- 辅 skill：`verification-before-completion`

**具体工作**
- 完成版本收口、历史留存和正式发布前检查
- 确认当前版本是否可以对外发布
- 将历史版本快照归档到版本目录

**强制规则**
- 每次正式修订前必须先留快照
- 版本号递增后不得再回写旧稿
- 历史版本不得覆盖，只能追加保存

### 14.1 何时算正式修订

以下任一情况，均视为正式修订：

- 修改流程节点、节点顺序或节点定义
- 修改主责人、审批人、校验人或知会人规则
- 修改时限、SLA、升级路径或冲突裁定规则
- 修改版本管理规则本身
- 修改交付标准、表单模板或冻结条件

仅修正文案措辞、错别字、排版，不影响执行口径的，不视为正式修订。

### 14.2 谁负责触发版本快照

- **主责人**：产品经理
- **归档执行人**：产品助理或登记专员
- **最终确认人**：产品负责人

每次正式修订开始前，产品经理必须先确认是否构成正式修订；一旦构成正式修订，归档执行人必须先生成历史快照，再进入正文修改。

### 14.3 版本号何时递增

- 版本号在**正式修订内容确认**后、**对外发布前**递增。
- 草稿阶段可以反复修改正文，但版本号不递增。
- 一旦版本号递增，即视为该稿进入发布候选状态，不得再与上一版混用。

### 14.4 保留与发布规则

1. **禁止直接覆盖历史版本**：每次修订前，必须先保留上一版历史文件。
2. **保留版本快照**：历史版本应保存在 `docs/versions/` 目录下，文件名包含原文档名、版本号和日期。
3. **修订记录留痕**：每次发布新版本时，应在文档头部或单独的变更记录中写明修改摘要。
4. **回滚依据明确**：如新版本发布后需要回退，应以最近一次稳定版本为基准恢复，不得直接覆盖历史文件。
5. **版本号递增示例**：`V1.0` -> `V1.1` -> `V1.2` -> `V1.3` -> `V1.4` -> `V1.5`

**建议文件命名规则**
- 当前版本：`产品需求管理流程规范.md`
- 历史版本：`产品需求管理流程规范_v1.0_20260509.md`
- 历史版本：`产品需求管理流程规范_v1.1_20260509.md`
- 历史版本：`产品需求管理流程规范_v1.3_20260509.md`
- 历史版本：`产品需求管理流程规范_v1.4_YYYYMMDD.md`
- 新版本：`产品需求管理流程规范_v1.5_YYYYMMDD.md`

## 15. 工作产出物管理规则

15.1 为保证产品工作流中的产出物可追溯、可备份、可恢复、可审计，统一规范工作产出物的定义、版本、变更、归档、恢复和废弃管理，特制定本规则。

15.2 本规则适用于产品工作流中所有需要进入流程管理、影响后续决策或执行、并应纳入版本管理和归档管理的正式产出物。

15.3 本规则所称正式产出物，包括但不限于：
- 需求登记单
- 需求分级结果
- 需求分析稿
- 方案说明
- 评审纪要
- 冻结版需求说明
- 交付包
- 变更单
- 复盘记录
- 版本快照
- 历史版本文件
- 与主文档绑定的附件文件

15.4 下列内容不视为正式产出物，除非被明确转正：
- 口头讨论内容
- 聊天记录
- 临时截图
- 临时表格
- 未纳入流程的个人草稿
- 仅供参考的中间材料

15.5 **正式产出物**指已进入流程节点、需要团队依赖、会影响后续决策或执行，并必须纳入版本管理和归档管理的文件或记录。

15.6 **草稿**指尚在整理中、未经过正式校验、未进入节点确认的文件。草稿可修改，但不视为正式版本。

15.7 **冻结件**指经过确认后不再随意修改、作为后续执行基线的正式版本。

15.8 **归档件**指已完成当前流程职责、进入历史留存状态、原则上不再编辑的文件。

15.9 **临时记录**指为协作便利形成的中间材料，不自动纳入正式版本库，除非被确认转正。

15.10 **统一版本库**指用于集中保存正式产出物当前版本、历史版本、归档版本和废弃版本的受控存储位置。

15.11 每个正式产出物必须明确以下责任角色：
- **创建人**：首次生成该文件或该版本的人
- **内容负责人**：对内容正确性、完整性和业务一致性负责的人
- **归档执行人**：负责备份、命名、入库和快照留存的人
- **最终确认人**：对该产出物是否可作为正式版本生效做最终确认的人

15.12 正式产出物至少应具备完整责任链。确因人员配置受限无法完全分离时，应保留原因记录，并由最终确认人进行抽检确认。

15.13 同一人同时承担创建、内容、归档、确认中多个角色的，应在记录中注明原因，不得默认视为流程合规。

15.14 所有正式产出物必须具备唯一编号，并可关联至需求编号、节点编号、版本号和归档日期。

15.15 正式产出物版本号必须递增管理，不得在正式版本上直接覆盖修改而不留痕。

15.16 建议命名格式为：
`[产出物名称]_[需求编号]_[版本号]_[日期]`

15.17 原型、流程图、字段表、规则表、验收标准等附件必须与主文档版本绑定，且版本一致。

15.18 主文档与附件一旦出现版本不一致，应立即暂停该产出物继续流转，不得以任一方单独作为准据版本继续推进。

15.19 版本不一致时，处理原则如下：
- 先以冻结版本作为唯一基线进行核对
- 完成主文档与附件的同步修正
- 修正完成后重新校验一致性
- 校验通过前，不得进入下一流程节点

15.20 任何版本不一致都视为待纠错状态，不视为有效正式版本。

15.21 任何正式产出物在修改前，必须先生成历史快照，再修改正文。

15.22 冻结后的正式产出物如需修改，必须先发起变更单，经审批后方可修改。

15.23 变更至少应包含：
- 变更提出人
- 变更原因
- 变更影响范围
- 变更审批人
- 归档执行人

15.24 以下行为禁止：
- 未备份直接覆盖正式版本
- 以口头同意替代变更记录
- 以聊天结论替代正式版本
- 未留痕删除旧版本
- 在附件版本未同步的情况下单独修改主文档

15.25 冻结后仅允许以下类型修改：
- 通过变更单批准的修改
- 不影响执行口径的纯格式修正，但必须留痕
- 经特批后形成的临时修订，但必须补齐正式变更记录

15.26 这里所称“纯格式修正”，仅限不改变业务含义、字段口径、流程顺序、责任归属、验收标准和依赖关系的修正。

15.27 下列情形不属于纯格式修正，必须走变更单：
- 改变业务含义
- 改变字段口径
- 改变流程顺序
- 改变责任归属
- 改变验收标准
- 改变依赖关系
- 改变附件与主文档的版本关系

15.28 如无法明确证明修改不影响业务含义，则不得按纯格式修正处理，必须走变更单。

15.29 任何冻结后修改都必须留痕。

15.30 留痕内容指的是：这次改了什么、为什么改、谁改的、谁确认的。对于纯格式修正，留痕内容至少应包括：
- 修改版本号
- 修改位置
- 修改前内容
- 修改后内容
- 修改人
- 确认人
- 修改时间
- 修改原因
- 是否影响业务含义
- 留痕载体或记录位置

15.31 留痕位置指的是：上述信息要记录到哪里。留痕记录应写入以下任一正式载体，并保持与产出物版本绑定：
- 版本变更记录
- 归档日志
- 批注记录
- 变更单附件

15.32 所有正式产出物必须进入统一版本库管理，不得长期散落在个人设备、聊天记录或临时目录中。

15.33 建议统一版本库至少分为以下目录：
- `drafts`：草稿
- `current`：当前正式版本
- `versions`：历史版本快照
- `archived`：归档件
- `obsolete`：废弃件

15.34 不同目录的权限建议如下：
- 草稿目录：允许编辑
- 当前正式版本目录：受控编辑
- 历史版本目录：只读
- 归档目录：只读
- 废弃目录：只读

15.35 正式产出物必须在以下必归档点完成归档，且仅在以下必归档点完成归档。冻结稿与正式发布稿视为不同版本对象，分别归档；同一版本对象在同一状态链中仅归档一次：
- 评审通过并进入冻结时
- 冻结稿正式发布时
- 变更单生效并形成新正式版本时
- 版本废弃前
- 复盘结论定稿并形成正式记录时

15.36 归档不得替代变更，变更不得替代归档。归档是留存动作，不是修改动作。

15.37 归档后若需继续修改，必须先进入变更流程，再生成新版本，不得直接覆盖归档件。

15.38 任何正式版本发布前，归档执行人必须确认：
- 文件齐套
- 版本正确
- 附件一致
- 历史快照已留存

15.39 正式产出物的标准状态为：
- 草稿
- 评审中
- 冻结
- 正式发布
- 归档
- 废弃

15.40 正式产出物的状态迁移规则如下：
- 草稿可进入评审
- 评审通过后方可进入冻结
- 冻结后方可进入正式发布
- 正式发布后方可进入归档
- 归档后原则上不再编辑
- 废弃件不得作为当前版本使用

15.41 冻结后允许的修改，必须通过变更流程处理，不得私下改动。

15.42 正式发布后如需修订，应生成新版本，并保留原版本，不得直接覆盖。

15.43 废弃后如需恢复，必须从历史版本恢复，并记录恢复原因、恢复人和确认人。

15.44 一旦发现文件丢失，应优先从历史版本或快照恢复。

15.45 恢复时应记录：
- 丢失范围
- 恢复来源
- 恢复时间
- 恢复人
- 确认人

15.46 以下情形可进入废弃：
- 已被新版本替代
- 需求取消
- 方案不再采用
- 文件内容已失效且不再使用

15.47 废弃件必须保留，不得直接删除。

15.48 任何正式产出物必须同时满足以下条件：
- 有唯一编号
- 有版本号
- 有创建人
- 有内容负责人
- 有归档执行人
- 有最终确认人
- 有历史快照
- 有可追溯路径
- 有附件一致性
- 有变更记录

15.49 缺少任一项，不得视为正式产出物完成。

15.50 下列行为视为违规：
- 未备份就覆盖
- 正式版本直接删除
- 冻结后未走变更单私自修改
- 附件版本与主文档不一致
- 没有归档即宣称完成
- 文件丢失后不做恢复记录

15.51 违规事项应记录原因、责任人、处理结果和整改措施。

15.52 建议先纳入强管控的正式产出物包括：
- 需求登记单
- 需求分析稿
- 冻结版需求说明
- 交付包
- 变更单
- 历史版本快照

15.53 后续可扩展纳入：
- 评审纪要
- 复盘记录
- 附件文件
- 临时分析表转正件
